Onboarding tutorial — Allegro project layout, Colab as GPU only

The first onboarding milestone proved you can run Llama-3.2-1B inference on a Colab T4. This tutorial walks you through the next step: moving the code into the Allegro Lab project layout — a paper/ submodule plus an experiments/ tree — edited locally with Claude Code and only sent to Colab when a GPU is actually needed.

1. Why move off the notebook

A notebook is a great demo. It's a bad codebase.

Right now the entire pipeline lives in notebooks/llama_pipeline.ipynb. That's been useful — it proved the model loads and generates on a T4. But notebooks have problems that get worse as the project grows:

  • Diffs are unreadable. A one-line code change shows up in the diff as 200 lines of JSON. Code review on GitHub becomes painful.
  • Hidden state. Cells that ran out of order can produce results no one can reproduce.
  • No reuse. If a function lives in cell 7 of one notebook, the next experiment copies and edits it instead of importing it.
  • Tooling can't help. Linters, type checkers, tests, and Claude Code all work much better on plain .py files.
The principle Keep logic in .py files. Use notebooks only as a thin driver on Colab — a few cells that import from your package and run it. No business logic should live inside a notebook cell.

2. The new workflow at a glance

┌────────────────────┐ ┌────────────────────┐ ┌────────────────────┐ │ Your laptop │ push │ GitHub │ pull │ Google Colab │ │ (CPU, no GPU) │ ──────▶ │ this repo │ ──────▶ │ (T4 GPU) │ │ │ │ │ │ │ │ • Edit .py files │ │ • Source of truth │ │ • Clone repo │ │ • Claude Code │ │ • Issues / PRs │ │ • pip install -e .│ │ • git commit │ │ │ │ • Run experiment │ │ • git push │ │ │ │ • Save CSV → git │ └────────────────────┘ └────────────────────┘ └────────────────────┘

You stop writing code in Colab. Colab becomes a GPU you rent for free, nothing more. All editing happens on your laptop with Claude Code, in real files you commit to git.

3. The Allegro project layout

Two folders. That's the whole rule.
glamor-research-onboarding/ ├── paper/ ← git submodule → the paper's GitHub repo └── experiments/ ← one folder per experiment
  • paper/ is a git submodule pointing at the project's paper repo on GitHub. One paper repo per project. Until there's a real paper, point it at an empty placeholder — the convention matters more than the contents.
  • experiments/<name>/ is self-contained. Whatever's needed to reproduce one figure or one table lives in that folder. The shape inside is up to the experiment; don't pre-design it.
Why no src/ layout? Research code is read more than it's imported. A reviewer (or future-you) cds into one experiment folder and sees everything in one place. A src/ package layout is for libraries; experiments aren't libraries.

4. The prompts on your laptop

You don't run the shell commands. You ask Claude Code to.

The whole point of this onboarding step is to stop hand-typing setup commands and start describing intent. Open Claude Code in any directory and use these prompts in order.

4.1 Prompt — clone and open the repo

In Claude Code, type:

Clone https://github.com/natSegOS/glamor-research-onboarding
into ~/Desktop/projects, then open the repo. Don't make any edits yet —
just clone it and show me the top-level files.

Claude will run git clone, ls, and show you what's inside. If anything looks wrong, ask it to fix it before moving on.

4.2 Re-open Claude Code inside the repo

Exit the current Claude Code session. In your terminal:

cd ~/Desktop/projects/glamor-research-onboarding
claude
Why a new session? Claude Code anchors to the directory it was started in. Running it from inside the repo means it reads CLAUDE.md (if present), respects .gitignore, and treats this project as its workspace.

4.3 Prompt — set up the local environment

In the new session, type:

Set up this repo for local editing. I won't run the model on my laptop —
I'll run it on Colab. Locally I just need imports to resolve so you can
read the code. Create a venv, replace the broken requirements.txt with a
real pyproject.toml, and install the deps.

Claude will read what's in the repo, propose the changes, and (with your approval) execute them. You watch and approve — you don't type the commands.

4.4 Prompt — use Colab as a remote GPU

Now ask Claude to set up the Colab side. Claude can't reach Colab itself, so its job is to write the notebook and tell you exactly what to paste.

I want to use Google Colab as a GPU only — all editing happens here in
Claude Code. Create experiments/trajectory_divergence/colab.ipynb as a
5-cell driver that: clones this repo with submodules, pip-installs it,
logs into Hugging Face, runs experiments/trajectory_divergence/run.py,
and downloads the CSV back. Then walk me through opening it in Colab,
switching the runtime to T4, and running the cells in order.

Claude writes the notebook into the repo. You open colab.research.google.com, File → Upload notebook, pick the colab.ipynb from the cloned repo, switch runtime to T4, and run cells top-to-bottom.

The pattern Anything that needs a GPU, you ask Claude to prepare locally — a notebook, a config, a script — then you push to GitHub, pull on Colab, and run. Claude is your editor; Colab is your renderer.
